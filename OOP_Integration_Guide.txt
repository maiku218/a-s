PILLAR 1: ENCAPSULATION (3 EXAMPLES)
==================================================

Definition: Bundling data (attributes) and methods that operate on that data
into a single unit (class), while restricting direct access to internal state.

Example 1: Product Class Encapsulation (models.py, lines 63-180)
------------------------------------------------------
- All sensitive fields are PRIVATE: _price, _stock, _name, _barcode, etc.
- External code CANNOT do: product._stock = -50  (would violate business rule)
- External code MUST use: product.stock = 100  (goes through setter validation)

Evidence in code:
    class Product(IEntity):
        def __init__(self, ...):
            self._price = Decimal(str(price))      # PRIVATE
            self._stock = int(stock)               # PRIVATE
        
        @property
        def price(self) -> Decimal:
            return self._price                     # READ-ONLY access
        
        @price.setter
        def price(self, value):                     # VALIDATED write access
            if value is None or Decimal(str(value)) < 0:
                raise ValueError("Price cannot be negative.")
            self._price = Decimal(str(value))

Usage in app.py (line ~1836):
    product = Product(
        product_id=0,
        name=request.form.get('product_name'),
        price=float(request.form.get('price', 0)),
        stock=int(request.form.get('stock', 0)),
        ...
    )
    # product.price setter automatically validates the value

Example 2: StockMovement Class Encapsulation (models.py, lines 23-61)
------------------------------------------------------
- PRIVATE fields: _movement_type, _quantity, _reason
- Public methods control how movement data is accessed
- Prevents invalid state changes

Evidence:
    class StockMovement:
        IN = 'IN'
        OUT = 'OUT'
        
        def __init__(self, ...):
            self._movement_type = movement_type   # controlled through constructor
        
        def is_inbound(self) -> bool:
            return self._movement_type == self.IN  # safe read-only access

Example 3: User/Cashier Status Encapsulation (models.py, lines 137-156)
------------------------------------------------------
- Cashier._status is PRIVATE
- Status can only be 'Active' or 'Inactive' (enforced by setter)

Evidence:
    class Cashier(User):
        @property
        def status(self) -> str:
            return self._status
        
        @status.setter
        def status(self, value: str):
            if value not in ('Active', 'Inactive'):
                raise ValueError("Status must be Active or Inactive.")
            self._status = value

PILLAR 2: INHERITANCE (3 EXAMPLES)
==================================================

Definition: A class can inherit attributes and methods from another class,
promoting code reuse and establishing a natural hierarchy.

Example 1: User Base Class (models.py, lines 114-131)
------------------------------------------------------
- Admin and Cashier both inherit from User
- Common attributes (id, username, full_name, password_hash) defined ONCE in User
- Common method verify_password() shared by both subclasses

Evidence:
    class User(IEntity):
        def __init__(self, user_id, username, full_name, password_hash):
            self._id = user_id
            self._username = username
            self._full_name = full_name
        
        def verify_password(self, password: str) -> bool:
            return check_password_hash(self._password_hash, password)

        def __init__(self, user_id, username, full_name, password_hash):

        def _log_login(self, mysql, request):  # Admin-specific method

Example 3: Cashier Inherits from User (models.py, lines 168-198)
------------------------------------------------------
- Cashier gets User properties + adds status field
- Cashier-specific method: log_logout()

Evidence:

Benefit: If User gains a new feature (e.g., last_login), Admin and Cashier

PILLAR 3: POLYMORPHISM (3 EXAMPLES)
==================================================

Definition: Different classes can be treated through the same interface,
but each class provides its own implementation of that interface.

Example 1: Polymorphic Authentication (services.py, lines 85-112)
------------------------------------------------------
- Both Admin and Cashier have authenticate() method
- Same interface, DIFFERENT behavior

Evidence in models.py:
    class Admin(User):
        def authenticate(self, password, mysql, request):
            if not self.verify_password(password):
                return False, None
            self._log_login(mysql, request)  # Admin logs to admin_activity
            return True, self

    class Cashier(User):
        def authenticate(self, password, mysql, request):
            if not self.verify_password(password):
                return False, None
            self._log_login(mysql, request)  # Cashier logs to cashier_activity
            return True, self

Used in services.py (line 85):
    def login(self, username, password, request, mysql, user_type='admin'):
        user = self._fetch_user(username, user_type, mysql)
        user_from_db = self._hydrate_user(user, user_type, mysql)
        success, result_user = user_from_db.authenticate(password, mysql, request)
        # ^^^ SAME METHOD CALL, but Admin and Cashier do different things!

Example 2: Polymorphic Stock Movement Processors (models.py, lines 201-280)
------------------------------------------------------
- Base class: StockMovementProcessor
- Two implementations: StockInProcessor (adds stock) and StockOutProcessor (removes stock)
- Client code uses same interface:

Evidence:
    class StockMovementProcessor:
        def process(self, product: Product):
            raise NotImplementedError  # subclasses override
    
    class StockInProcessor(StockMovementProcessor):
        def process(self, product: Product):
            product.apply_movement(self.movement.quantity, StockMovement.IN)
            self._record_movement(product)
    
    class StockOutProcessor(StockMovementProcessor):
        def process(self, product: Product):
            product.apply_movement(self.movement.quantity, StockMovement.OUT)
            self._record_movement(product)

Usage in app.py:
    movement = StockMovement(..., movement_type=StockMovement.IN, ...)
    product_repository.link_stock_movement(product, movement)
    # Factory returns correct processor automatically
    # No if/else needed in client code!

Example 3: Polymorphic Sale Processing (services.py, lines 188-270)
------------------------------------------------------
- SalesService.process_sale() handles both Medical and Non-Medical items
- Polymorphism at work: same method, different internal logic for each type

Evidence in services.py:
    def _process_sale_impl(self, items, cashier, cur):
        medical_items = []
        non_medical_items = []
        
        for item in items:
            cur.execute("SELECT product_type FROM products WHERE id=%s", (item['id'],))
            result = cur.fetchone()
            product_type = result[0] if result else 'Non-Medical'
            if product_type == 'Medical':
                medical_items.append(item)   # Processed differently
            else:
                non_medical_items.append(item)  # Processed differently
        
        if medical_items:
            receipt_number, sale_total, sale_items = self._create_sale(
                cur, medical_items, cashier.id, 'Medical'
            )
        if non_medical_items:
            receipt_number, sale_total, sale_items = self._create_sale(
                cur, non_medical_items, cashier.id, 'Non-Medical'
            )

PILLAR 4: ABSTRACTION (3 EXAMPLES)
==================================================

Definition: Hiding complex implementation details behind a simple interface.
Users of the class only need to know WHAT it does, not HOW it does it.

Example 1: IRepository Abstraction (models.py, lines 18-32)
------------------------------------------------------
- IRepository defines the CONTRACT: get_all(), get_by_id(), save(), delete()
- ProductRepository IMPLEMENTS this contract
- Clients (routes, services) work with the interface, not raw SQL

Evidence in models.py:
    class IRepository(ABC):
        def get_all(self): ...           # Abstract contract
        def get_by_id(self, entity_id): ...
        def save(self, entity): ...
        def delete(self, entity_id): ...

    class ProductRepository:
        def find_by_id(self, product_id: int) -> Optional[Product]:
            cur = self.mysql.connection.cursor()
            try:
                cur.execute("SELECT ... FROM products WHERE id=%s", (product_id,))
                row = cur.fetchone()
                return self._row_to_product(row)  # hides SQL details
            finally:
                cur.close()

Client code (services.py) NEVER sees raw SQL:
    product = product_repository.find_by_id(product_id)
    # ^^^ Simple interface, SQL hidden behind abstraction

Example 2: IAuthService Abstraction (services.py, lines 12-28)
------------------------------------------------------
- IAuthService defines contract: login(), logout(), get_session_data()
- AuthService implements it
- Routes call simple methods instead of handling raw SQL and session logic

Evidence in services.py:
    class IAuthService(ABC):
        @abstractmethod
        def login(self, username, password, request, mysql, user_type):
            ...  # Contract: returns (success, user)
        
        @abstractmethod
        def get_session_data(self, user):
            ...  # Contract: returns session dict

Client code in app.py (line ~1836):
    success, user = auth_service.login(username, password, request, mysql, 'admin')
    if success and user:
        session_data = auth_service.get_session_data(user)
        session.update(session_data)
        # ^^^ Route doesn't know HOW login works, just THAT it works

Example 3: ISalesService Abstraction (services.py, lines 32-37)
------------------------------------------------------
- ISalesService defines: process_sale()
- SalesService implements all the complex sale logic
- Routes just call one method

Evidence:
    class ISalesService(ABC):
        @abstractmethod
        def process_sale(self, items: list, cashier: Cashier) -> dict:
            ...  # Returns success/failure dict

Client code in app.py (line ~1860):
    result = sales_service.process_sale(enriched_items, cashier)
    return jsonify(result)
    # ^^^ Route doesn't handle stock updates, receipt generation, etc.
    #     All that complexity is ABSTRACTED away in SalesService

==================================================
PRESENTATION TALKING POINTS
==================================================

1. ENCAPSULATION: "Gamit nato ang Product class diin ang price ug stock kay
   PRIVATE. Dili maka-change ang external code diretso. Kinahanglan mo-pass
   sa setter nga nag-validate sa value. Para malikayan ang invalid data."

2. INHERITANCE: "May base class nga User. Ang Admin ug Cashier mag-inherit
   niya. Share nila ang parehas nga method nga verify_password(). Kung mag-
   -update ta sa User, naa dayon sa Admin ug Cashier."

3. POLYMORPHISM: "Parehas nga method nga authenticate() sa Admin ug Cashier,
   pero lahi ang ilang implementation. Admin logs to admin_activity, Cashier
   logs to cashier_activity. Mao na ang polymorphism - same interface,
   different behavior."

4. ABSTRACTION: "Gamit nato ang IAuthService interface. Dili kinahanglan
   mohibal-an sa route handler kung unsa ang process sa login. I-call lang
   nila ang auth_service.login(). Hidden na ang SQL queries ug session logic."
