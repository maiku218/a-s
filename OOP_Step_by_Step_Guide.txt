Project: Pharmacon - Pharmacy Management System

==================================================
OVERVIEW
==================================================

Your system now uses THREE main files working together:

  app.py      = Flask routes (the "controller" - handles HTTP requests)
  models.py   = Domain classes (Product, User, Admin, Cashier, StockMovement)
  services.py = Business logic (AuthService, ProductRepository, SalesService)

All 4 pillars are present. Here is how each file uses them.

==================================================
HOW THE 3 FILES WORK TOGETHER
==================================================

STEP 1: User visits the website
  -> Browser sends HTTP request to Flask
  -> app.py route catches the request (e.g., @app.route('/admin_login'))

STEP 2: Route calls a Service
  -> app.py calls auth_service.login() OR product_repository.save()
  -> The Service contains the business logic (no SQL in the route!)

STEP 3: Service uses Models
  -> Services create User, Product, StockMovement objects
  -> Models enforce business rules (validation, encapsulation)

STEP 4: Service talks to the Database
  -> Services run SQL queries internally
  -> Routes never see raw SQL or database connections

STEP 5: Response returned to user
  -> Service returns a simple result (True/False, dict)
  -> Route sends the response back to the browser

==================================================
PILLAR 1: ENCAPSULATION (in models.py)
==================================================

WHAT IT IS:
  Putting data and methods together in a class, and hiding the internal
  data so only the class itself can change it directly.

WHY WE USE IT:
  Prevents invalid data. Example: Nobody can set product price to negative
  number because the Product class checks it first.

HOW IT WORKS IN YOUR CODE:

  In models.py (lines 97-209):

    class Product:
        def __init__(self, ...):
            self._price = Decimal(str(price))   # PRIVATE - underscore prefix
            self._stock = int(stock)             # PRIVATE

        @property
        def price(self):
            return self._price                   # READ: anyone can read

        @price.setter
        def price(self, value):
            if value < 0:
                raise ValueError("Price cannot be negative!")  # VALIDATE
            self._price = value                 # WRITE: only if valid

  HOW TO USE IT:

    In app.py (line ~1850):
        product = Product(name="Paracetamol", price=10.00, stock=100)
        product.price = -50          # ERROR! ValueError raised
        product.stock = -10          # ERROR! ValueError raised
        print(product.price)         # OK! Returns 10.00

  MORE EXAMPLES IN YOUR CODE:
    1. StockMovement (models.py lines 42-94): _movement_type is private,
       only is_inbound() or is_outbound() can check it safely.
    2. Cashier.status (models.py lines 308-316): Status can only be
       'Active' or 'Inactive', nothing else is allowed.

PILLAR 2: INHERITANCE (in models.py)
==================================================

WHAT IT IS:
  A child class can copy all the features of a parent class and add
  its own new features. This avoids repeating the same code.

WHY WE USE IT:
  Admin and Cashier both need username, password, and verify_password().
  Instead of writing it twice, we write it once in User, and both
  Admin and Cashier inherit from it.

HOW IT WORKS IN YOUR CODE:

  In models.py (lines 216-352):

    class User:                           # PARENT CLASS
        def __init__(self, username, password_hash):
            self._username = username
            self._password_hash = password_hash

        def verify_password(self, password):
            return check_password_hash(self._password_hash, password)

    class Admin(User):                    # CHILD CLASS - inherits from User
        def _log_login(self, mysql, request):
            # Admin-specific code (logs to admin_activity table)

    class Cashier(User):                  # CHILD CLASS - inherits from User
        def log_logout(self, mysql):
            # Cashier-specific code (logs to cashier_activity table)

  WHAT IS INHERITED:
    Admin gets: _username, _password_hash, verify_password(), and ALL User methods
    Cashier gets: _username, _password_hash, verify_password(), and ALL User methods

  HOW TO USE IT:

    In app.py or services.py:
        admin = Admin(1, "admin", "Admin User", hashed_password)
        print(admin.username)              # Inherited from User
        print(admin.verify_password("abc")) # Inherited from User
        admin._log_login(mysql, request)    # Admin's own method

        cashier = Cashier(2, "juan", "Juan Dela Cruz", hashed_pw)
        print(cashier.username)            # Inherited from User
        cashier.log_logout(mysql)           # Cashier's own method

  BENEFIT:
    If we add a new feature to User (e.g., last_login timestamp),
    both Admin and Cashier automatically get it. No need to change them!

PILLAR 3: POLYMORPHISM (in models.py + services.py)
==================================================

WHAT IT IS:
  Same method name, different behavior depending on which class calls it.
  Like a universal remote - same buttons, works on different TVs.

WHY WE USE IT:
  We want to call user.authenticate() for both Admin and Cashier, but
  they do different things. Admin logs to admin_activity, Cashier logs
  to cashier_activity. Polymorphism lets us use one simple call.

HOW IT WORKS IN YOUR CODE:

  Example 1: authenticate() method (models.py lines 254-323)

    class Admin(User):
        def authenticate(self, password, mysql, request):
            if self.verify_password(password):
                self._log_login(mysql, request)  # Logs to admin_activity
                return True, self
            return False, None

    class Cashier(User):
        def authenticate(self, password, mysql, request):
            if self.verify_password(password):
                self._log_login(mysql, request)  # Logs to cashier_activity
                return True, self
            return False, None

  HOW SERVICES USE IT (services.py lines 51-66):

    def login(self, username, password, request, mysql, user_type):
        user = self._fetch_user(username, user_type, mysql)
        user_from_db = self._hydrate_user(user, user_type, mysql)
        
        # SAME METHOD CALL for both Admin and Cashier:
        success, result_user = user_from_db.authenticate(password, mysql, request)
        
        return success, result_user

    Notice: The service does NOT check "if admin: do this, if cashier: do that"
    It just calls .authenticate() and lets the object handle itself!

  Example 2: Stock Movement Processors (models.py lines 358-413)

    class StockMovementProcessor:
        def process(self, product):
            raise NotImplementedError  # Child classes must override

    class StockInProcessor(StockMovementProcessor):
        def process(self, product):
            product.apply_movement(quantity, StockMovement.IN)  # ADDS stock
            self._record_movement(product)

    class StockOutProcessor(StockMovementProcessor):
        def process(self, product):
            product.apply_movement(quantity, StockMovement.OUT) # REMOVES stock
            self._record_movement(product)

  Factory function (models.py line 407):

    def get_movement_processor(movement, mysql):
        if movement.is_inbound():
            return StockInProcessor(movement, mysql)
        elif movement.is_outbound():
            return StockOutProcessor(movement, mysql)

  HOW TO USE IT (in app.py or services.py):
    movement = StockMovement(1, 10, 'IN', 50, 'Stock Addition')
    processor = get_movement_processor(movement, mysql)
    processor.process(product)  # Calls StockInProcessor.process()
                                # Same call, different behavior!

PILLAR 4: ABSTRACTION (in models.py + services.py)
==================================================

WHAT IT IS:
  Hiding complex details behind a simple interface. Users only see WHAT
  something does, not HOW it does it.

WHY WE USE IT:
  Routes in app.py should NOT know about SQL queries, database connections,
  or table structures. They should just call simple methods like
  "save this product" or "login this user".

HOW IT WORKS IN YOUR CODE:

  Example 1: ProductRepository hides SQL (models.py + services.py)

    THE INTERFACE (what routes see):
        product_repository.save(product)           # Simple!
        product_repository.find_by_id(5)           # Simple!
        product_repository.count_low_stock()       # Simple!

    THE HIDDEN IMPLEMENTATION (what routes DON'T see):
        def save(self, product: Product):
            cur = self.mysql.connection.cursor()
            cur.execute("""
                INSERT INTO products (product_name, barcode, ...)
                VALUES (%s, %s, ...)
            """, (product.name, product.barcode, ...))
            self.mysql.connection.commit()
            cur.close()

    HOW TO USE IT (in app.py):
        # Route doesn't write any SQL!
        product = Product(name="Paracetamol", price=10.00, stock=100)
        product_repository.save(product)  # SQL is hidden inside

  Example 2: AuthService hides login logic (services.py lines 15-135)

    THE INTERFACE:
        success, user = auth_service.login(username, password, request, mysql, 'admin')

    THE HIDDEN IMPLEMENTATION:
        - Connects to database
        - Checks if user exists
        - Creates default admin if needed
        - Verifies password hash
        - Logs login activity
        - Returns User object

    HOW TO USE IT (in app.py):
        # Route just calls one simple method:
        success, user = auth_service.login(username, password, request, mysql, 'admin')
        if success:
            session.update(auth_service.get_session_data(user))

        All the SQL and session logic is hidden inside AuthService!

  Example 3: ISalesService interface (services.py lines 35-41)

    THE INTERFACE:
        result = sales_service.process_sale(items, cashier)

    THE HIDDEN IMPLEMENTATION:
        - Validates items
        - Separates medical/non-medical
        - Creates sales records
        - Updates stock
        - Logs stock movements
        - Generates receipt

    HOW TO USE IT (in app.py):
        # Route calls ONE method:
        result = sales_service.process_sale(items, cashier)
        return jsonify(result)

        The route has NO idea how sales are processed. All complexity
        is hidden inside SalesService!

PRESENTATION SUMMARY (Talking Points)
==================================================

1. ENCAPSULATION in models.py:
   "Ang product class nag-control sa iyang kaugalingong data. Dili maka-
   change ang external code sa price stock diretso. Kinahanglan mo-pass
   sa setter nga nag-validate. Para walay negative price o stock."

2. INHERITANCE in models.py:
   "May base class nga User. Admin ug Cashier mag-inherit niya. Share
   nila ang parehas nga method nga verify_password(). Kung mag-update ta
   sa User, naa dayon sa Admin ug Cashier. Less code duplication."

3. POLYMORPHISM in models.py + services.py:
   "Parehas nga method sa Admin ug Cashier nga authenticate(), pero lahi
   ang ilang implementation. Mao na ang polymorphism - same interface,
   different behavior. Cashier logs to cashier_activity, Admin logs to
   admin_activity."

4. ABSTRACTION in services.py:
   "Gamit nato ang ProductRepository. Dili kinahanglan mohibal-an sa
   route handler kung unsa ang SQL queries. I-call lang nila ang
   save() o find_by_id(). Hidden na ang details."
